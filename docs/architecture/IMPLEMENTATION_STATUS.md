# Architecture and reliability implementation status

Baseline: `6e138e2cb5a095c4cc0a856291430cf6a3b683fb` on `develop`.
Implementation branch: `refactor/develop-architecture-reliability`.
Date: 15 September 2026.

This is the first staged reliability update. It does **not** complete the comprehensive refactor. The implementation follows the specification's allowance for an independently reviewable foundation release before the feature migration and deployed outbox stage. Requirements below describe specific behaviours, not wholesale completion of a file or feature.

## Local continuation

The following uncommitted local changes continue A01/W07 without preserving whole-container compatibility paths:

- `ResolverWorkflowRunner` receives its resolver, progressive-response client and User gateway explicitly.
- `AvailabilityDialog` receives its progressive-response client explicitly.
- Playback speed, transport and queue-navigation Alexa adaptation is owned by `src.alexa.playback_controls.PlaybackControls`, which receives playback, User and catalogue collaborators explicitly. The obsolete `Playback.play_queue_delta(..., deps=...)` implementation is removed.
- Playback, report and rating handlers are constructed with explicit actions/collaborators in `RouteRegistry`.
- Feedback continuation receives the queue-navigation action explicitly.
- Fallback and unmatched-request handlers receive User and onboarding collaborators explicitly; onboarding town-capture retry no longer takes the whole container.
- Intent dispatch, identity middleware, resolver middleware and feedback gates now receive exact feature collaborators or injected actions. `ApplicationContainer` owns their construction.
- `Availability` now receives its Hear client, progressive-response client, User gateway, browse catalog owner and playback collaborator directly. Its direct search and search-to-playback calls also use explicit collaborators.
- `Affirmative` and `Decline` receive their state, dialogue, playback and delegated action collaborators explicitly. The composition root supplies their actions rather than either class retaining the application container.
- Feedback response actions, suggestion confirmation and the onboarding gate now receive explicit state, action and workflow collaborators. `FeedbackContinuation` receives the request-owned User gateway explicitly as well.
- Notification handling now receives its API, User, search/playback, permission and event collaborators explicitly. Permission completion uses a narrow notification-enable callback, removing the previous constructor cycle.
- Creator identity, follow and unfollow actions now use explicit User, feedback, event and followed-playback collaborators; the composition root supplies the followed-playback action.
- Launch workflow now receives its User, notification, playback, profile, listener-sync and town-capture collaborators directly.
- Town-capture and set-location actions now receive the User gateway, onboarding state service and explicit town workflow actions directly.
- The explicit search-to-playback boundary now includes the first-result playback path; it receives User, catalog and playback collaborators instead of a container.
- Content, creator and organisation playback actions now receive only User, Hear, progressive-response, catalogue/playback and narrow follow/pagination/city actions. Browse owns only its User, Hear, progressive-response and playback collaborators plus a recommendation action; it no longer retains the application container. Followed-source playback also uses explicit collaborators end-to-end.
- The onboarding workflow and permission-resume path now receive their exact onboarding, User, resolver, device-location, progressive-response and fallback collaborators. The obsolete `deps` parameter and onboarding dependency carrier are removed.
- `Application.build_skill` now accepts an explicitly named application container; Lambda diagnostic injection uses the same explicit name. No production feature or assembly API accepts a generic `deps` argument. Route declarations are immutable factories, so each dispatch builds fresh handlers and feature actions rather than reusing request-capable controller objects.
- `Playback` now requires its state store, queue store and event service at construction. Its play and resume helpers also require an explicit playback-state collaborator. Obsolete static session helpers and an unused queued-next implementation that silently created state are removed; no playback helper accepts a generic dependency bag.
- Search execution now accepts an immutable `SearchRequest` with validated query, intent, filters and pagination values. Browse, availability, followed-source playback and the content/creator/organisation actions no longer pass loose search-options dictionaries.
- Essential changes spanning two or more state scopes now use one conditional DynamoDB `TransactWriteItems` call. The persistence adapter retries a transaction only after reloading and domain-merging its affected scopes; independent non-essential scope writes remain separate.
- Feature events are staged on the request-owned User gateway and persisted as immutable `OUTBOX#<eventId>` records in the same conditional DynamoDB transaction as their state changes. The relay validates committed stream records, enqueues them to the existing SQS queue, then marks them sent; a bounded GSI recovery job handles pending records without scanning listener state.
- `RequestContext` is now bound once per invocation and retains only references to the SDK-owned transient maps. The report feature accepts that context plus a typed `ReportCommand` and returns a typed `ReportReceipt`; report response adaptation remains in its controllers.
- Feedback submission accepts a validated `FeedbackCommand` and returns a `FeedbackReceipt`; all feedback response actions and rating use the request context rather than raw Alexa slot values. Follow and unfollow now use a validated `FollowCommand`/`FollowReceipt` transition, and creator identity uses the same controller-owned request-context adaptation with one normalized source-type boundary.
- Audio-player controllers now adapt SDK requests into validated `PlaybackEventCommand` values. `src.alexa.playback_events.PlaybackEvents` receives `RequestContext`, applies started/nearly-finished/finished/stopped/failed/progress transitions, and returns `PlaybackEventReceipt`; controllers alone notify Alexa-facing services or build the callback response.
- `HearApiClient.bind()` now returns an immutable `ListenerBoundHearClient` with a captured request identity and no lifecycle ownership. Playback-control handlers, audio queue prefetch, the complete Browse/Availability discovery graph, content/creator/organisation playback, intent-dispatch playback actions, notification handlers, Yes/No dialogue actions and feedback/queue continuation actions create that client through `ApplicationContainer` per dispatch; the shared client/pool remains identity-free. Bootstrap identity/synchronisation remains intentionally application-scoped.
- Every production request/response interceptor now has an async `process` contract. The runtime rejects synchronous interceptors at registration instead of inspecting or adapting mixed styles at invocation.
- `ApplicationLog` is the single enable/disable switch for HEAR logs. It no longer changes Python's global logging state, and request logging records allowlisted structure only—not utterances, payloads, IDs/tokens, coordinates, or raw exception text.

The complete local unit suite passes: 1081 tests. The suite-wide socket guard permits only loopback connections required by Windows asyncio while continuing to reject external networking and DNS. The normal test configuration collects `tests/` only; the stateful Lambda exploration under `scratch/` remains opt-in. No local change has been committed or pushed.

## Compatibility and remaining risks

No wire fields or stored schema version changed. Stricter worker validation intentionally sends malformed or unsupported envelopes through existing SQS retries/redrive instead of acknowledging them. Existing v3 producer envelopes remain supported.

An essential write timeout is an **uncertain remote outcome**, not proof that DynamoDB rolled back. Independent non-essential scope operations can still partially commit. Feature state and its durable outbox record are written together, but a crash after SQS acceptance and before the sent marker can redeliver the same stable event; exactly-once delivery is not claimed and requires backend deduplication verification.

Source-level pool cleanup is covered for the current loop and closed-client replacement. Full application shutdown across managed loops still needs an explicit lifecycle integration.

Live Hear/Resolver OpenAPI retrieval was unavailable during this task. Checked-in contracts and callers informed this stage. There is no evidence permitting removal of `listeners/register` or `listeners/sync`.

The rollback code baseline is the pinned develop commit above; this stage preserves its physical state format. Production rollback and mixed-version integration have not been exercised.
