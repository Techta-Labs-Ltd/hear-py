2. FIX SEARCH PAGINATION (HIGH PRIORITY)
================================================================================

WHAT'S BROKEN:
  src/services/api.py:80-81
  _normalize_search_response reads data.get("total_hits") and
  data.get("total_pages") from the API response.

  The new API returns:
    { "total": 50, "totalPages": 1, ... }

  The code reads snake_case keys that do not exist:
    data.get("total_hits")   -> always None, falls back to len(results)
    data.get("total_pages")  -> always None

IMPACT:
  - Pagination logic in browse_catalog.py and play.py is broken
  - "Show more" / "next page" in browse will not work correctly
  - Total result counts are approximated from page length instead of
    reflecting the actual server total

FIX:
  src/services/api.py lines 80-81
  Change data.get("total_hits")  -> data.get("total")
  Change data.get("total_pages") -> data.get("totalPages")
  Also fix the error fallback on lines 122-123

DOWNSTREAM CONSUMERS (use "total_hits" and "total_pages" keys from
the normalized result):
  src/utils/browse_catalog.py        lines 133, 137
  src/handlers/intents/play.py       lines 258, 299

4. FIX TRACK-LEVEL CREATOR (HIGH PRIORITY)
================================================================================

WHAT'S BROKEN:
  src/handlers/audio/playback_nearly_finished.py line 191
  Reads track.get("creator")

  In the new API, track objects contain:
    id, title, categories, tags, audioUrl, shortDescription, durationSecs,
    playback_speed

  There is NO creator field at the track level. Creator only exists at
  the parent content item level.

IMPACT:
  feedbackCreator will always be None for track-based content (publications
  with tracks array). This affects feedback submission metadata.

FIX:
  line 191: track.get("creator") -> track.get("creator") or store.get("feedbackCreator")
  (fall back to the parent content's creator from persistence)

6. CREATOR FIELD TYPE — OBJECT vs STRING (AWARENESS)
================================================================================

The new API returns creator as an object:
  "creator": { "id": "...", "name": "Super Admin" }

normalize_content_item.py already handles this correctly via
_extract_creator_name() which extracts the name string from the dict.

However, these locations read item.get("creator") directly and could
receive a dict instead of a string if the item hasn't been normalized:
  src/handlers/audio/playback_failed.py  lines 103, 108
  src/handlers/intents/system.py         lines 335, 380, 625
  src/utils/browse_navigation.py         line 91
  src/utils/queue_advance.py             line 75

These are currently safe because they receive already-normalized items
(from get_content_by_id or from stored queue data). Once get_content_by_id
is removed, ensure all paths normalize content items before storing them
so creator is always a string by the time it's read.
